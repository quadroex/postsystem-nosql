# Відстеження поштових відправлень у NoSQL

Продовження проєкту [postsystem](https://github.com/quadroex/postsystem). Для перевірки достатньо цього README, збережених результатів і посилань на код.

## 1. Використані NoSQL бази

MongoDB - документна база. Кожне відправлення зберігається в одному документі разом із поточним статусом та масивом подій. За номером відправлення можна прочитати всю його історію.

Redis - база типу «ключ-значення». У нашому прикладі ключ містить номер відправлення, а значення - його останній статус. Статус можна прочитати за ключем, який автоматично зникає після закінчення строку дії.

## 2. Які дані можна винести

Для відстеження додано сканування на проміжних пунктах. Відправлення може мати кілька подій з тим самим статусом у різних відділеннях. Користувач зазвичай відкриває історію одного номера, тому події зручно зберігати поруч у документі. Це прибирає з’єднання таблиць під час читання картки, але назва відділення дублюється в подіях, а масив має обмежуватися.

Платежі, оформлення й аудит залишаються у PostgreSQL. Для них потрібні вже реалізовані зв’язки та транзакції. Якщо додати документну картку до робочого проєкту, її треба оновлювати разом із журналом.

Для заповнення баз тестовими даними використано ШІ, який допоміг написати генератор. Під час запуску цей генератор створює штучні відправлення та події за фіксованим алгоритмом, тому обидві бази отримують однакові записи. [Код генератора](src/TrackingData.cs).

## 3. Реалізація у MongoDB

У колекції `shipments` один документ відповідає одному відправленню. Він містить номер, поточний стан і масив `events`. Нова подія додається однією командою `updateOne`, яка одночасно оновлює стан і ревізію. Стара ревізія відхиляється. Код обмежує історію 64 подіями.

[Код MongoDB](src/MongoStore.cs). [Фактична картка і результат запитів](evidence/sample.json).

## 4. Та сама модель у PostgreSQL

У PostgreSQL дані одного документа MongoDB розподілено між трьома таблицями. У `tracking.shipments` зберігаються номер відправлення, останній статус, час оновлення та ревізія. Кожна подія має окремий рядок у `tracking.tracking_events`. Її визначає пара з номера відправлення та порядкового номера події. Назви відділень зберігаються в `tracking.branches`, а подія посилається на потрібне відділення через `branch_id`.

Історія зчитується одним запитом з трьох таблиць. Остання подія береться за порядковим номером. Список відділення відсортовано за часом і номером з лімітом 20. Один SQL-запит перевіряє ревізію, оновлює відправлення і додає подію. Довідник відділень у досліді не змінюється, тому назви в SQL і документах збігаються.

[Схема SQL](sql/schema.sql), [запити](src/PostgresStore.cs), [перевірки обох реалізацій](evidence/verify.txt).

## 6. Redis

Redis використано як кеш поточного статусу за номером відправлення. Приклад виконує `SET` зі строком дії, `GET`, `MGET`, оновлення існуючого ключа, `TTL` і `DEL`. Перевірено, що після закінчення строку ключ зникає. Кеш не є основним журналом відправлень і не входить у порівняння MongoDB з PostgreSQL.

[Команди Redis](redis/demo.sh), [фактичний вивід](evidence/redis.txt), [документація Redis](https://redis.io/docs/latest/commands/set/).

[Повторення досліду](docs/run.md). [Автоматична перевірка](https://github.com/quadroex/postsystem-nosql/actions).

## Висновок

MongoDB зручно зберігає картку відправлення разом з історією в одному документі. У наших замірах PostgreSQL із індексами збирав ту саму історію з трьох таблиць швидше й мав вищу пропускну здатність у всіх перевірених сценаріях. Тому для цього проєкту повний журнал доцільно залишити в PostgreSQL. Redis підходить для іншої задачі - тимчасово зберігати останній статус, коли потрібна лише коротка відповідь за номером відправлення.
